# File sync and privacy review (2026-10-20)

## Scope and evidence

This review follows a browser attachment from local storage through the sync client, a real local CashFlux server, and a second isolated browser profile. It also checks the Cloud setup and account-scope boundaries. The production host was queried only at its public `/v1/version` endpoint, without credentials or customer data. Its advertised API range includes this client's v1 protocol; production account data and production file transfer were not accessed.

The executable evidence is `e2e/regression/sv0_first_snapshot.spec.mjs`, `sv0_artifact_upload.spec.mjs`, `sv0_artifact_sync.spec.mjs`, `sv0_server_url.spec.mjs`, and `sv0_lock_reload.spec.mjs`, plus the server's blob isolation and quota tests in `internal/server/blobservice_test.go`, the blob-backed PDF snapshot test in `internal/appstate/artifact_roundtrip_test.go`, and local encrypted-store tests in `internal/artifactstore` and `internal/browserstore`. These tests use synthetic accounts and fresh local servers. Browser status text alone is never the file oracle: the upload tests inspect the server snapshot, and the full roundtrip compares downloaded bytes with the source PNG. The PDF completeness and local-store encryption cases are unit tests, not browser roundtrips.

## Current data flow

| Step | Behavior | Privacy boundary |
| --- | --- | --- |
| Local save | The app keeps the working dataset in protected browser storage. Dataset saves use a generation compare-and-swap so another tab cannot silently replace them. Large artifact bytes can live in a separate IndexedDB blob store. | New local artifact records seal bytes and MIME with the protected workspace key and bind them to the artifact ID. The active household's legacy plaintext records are migrated after unlock, and any older record is encrypted on first read before its bytes are returned. If the blob store is unavailable, bytes remain in the protected dataset. |
| First connection | Settings checks the public `/v1/version` response and establishes an account session. A first push creates an empty owned workspace row before uploading blobs. | Discovery sends no bearer token. Remote non-loopback sync requires HTTPS/WSS; loopback HTTP/WS remains available for local development. |
| File upload | `prepareBackendSyncDataset` encrypts each artifact with the App Lock passcode, uploads ciphertext under its SHA-256 hash, replaces bytes with a blob reference, then encrypts the dataset snapshot. The server links the blob to the authenticated workspace and enforces the account's storage quota. | The server receives ciphertext and `application/octet-stream`, not the filename, image MIME, or plaintext bytes for new encrypted uploads. It still sees sizes, hashes, workspace/account identifiers, and timing. |
| Blob-backed files | Before upload, the client completes the committed queue item with its matching local file bytes. It pauses sync when a required blob is missing, unreadable, or shorter than its recorded size. | A partial file cannot turn into a successful fileless snapshot. The queued metadata remains available for retry or local recovery. |
| File restore | A second device decrypts the snapshot using the same passcode, downloads each referenced blob through the authenticated workspace, checks the received ciphertext hash, decrypts it, and imports the original bytes. | A mismatched hash or decryption error aborts the import. The full browser test restored a PNG byte-for-byte in another profile. |

The server stores workspace names, device IDs, account identity, timestamps, ciphertext sizes, and blob hashes as readable metadata. Workspace names can contain sensitive words; they are **not** covered by the encrypted snapshot. Artifact encryption uses a per-install salt and a deterministic IV derived from plaintext, so an identical file uploaded twice with the same installation key produces the same ciphertext hash. That enables deduplication but reveals equality within that installation to the server. Passcode strength also matters because possession of ciphertext permits offline guessing attempts.

## Safety and recovery behavior

- Dataset and blob uploads require active encryption. The server rejects a plaintext replacement after it has seen an encrypted workspace. On migration to an encrypted snapshot, it purges plaintext snapshot history for that workspace in the same accepted transaction.
- Server workspace creation advances its version. The client now uses the returned version for the immediately following first snapshot push; a later write from another device still conflicts. A rejected local snapshot is retained as a recovery copy before the client pulls the server winner.
- After a server accepts the first snapshot, the app commits its account ownership in protected storage and lets the same app's autosave writer adopt that value. This prevents a false “another tab” read-only state without allowing another tab's owner change to pass its compare-and-swap.
- Changing the server clears the old refresh/access credentials, queue, and sync bookmarks before the new endpoint is used. The focused browser case passed after journal replay was moved off the WebCrypto callback stack: the new server had no copied account and the setup was signed out after unlock. An ordinary encrypted workspace reload also passed.
- JSON and SQLite single-workspace backups fail when required local file bytes cannot be read. The full-install backup now aborts if the active dataset export fails, and its file reads run outside the browser click callback.

## Limits and follow-up work

1. **Legacy local attachments:** New writes are encrypted and migration waits for a committed replacement. Active-household legacy files are visited after unlock and older entries migrate on access. Inactive workspace bundles or orphaned old records can remain plaintext until they are opened; a complete origin-wide migration needs workspace ownership mapping and a raw IndexedDB browser scan before App Lock can be described as protecting *all historical* attachments. `TODOS.md` tracks the broader ENC4 work.
2. **Metadata confidentiality:** Encrypt or deliberately minimize workspace names and other human-entered server metadata before describing sync as fully private. The current remote-content statement is limited to dataset and new attachment *contents*.
3. **Legacy data:** The client can still read legacy plaintext server blobs. A current encrypted snapshot does not prove every old blob, server backup, or operator backup has been erased. Operators must run documented retention and blob GC jobs and check their results; migration of legacy blob references needs a dedicated verification case.
4. **Backup completeness:** `/v1/account/export` returns snapshots but does not carry the blob payloads. A server export by itself is not a complete file backup. The full-install browser backup also takes inactive workspace bundles from their saved dataset strings and does not yet rehydrate their external file bytes. Both paths need a complete encrypted export/restore format and a restore test before they are described as file-complete recovery copies.
5. **Production validation:** The tests prove local protocol behavior. A credentialed production roundtrip would require a deliberately created test account and file, with explicit authorization and cleanup; no customer data should be used as a test fixture.
