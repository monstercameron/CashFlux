# File sync and privacy review (2026-10-20)

## Scope and evidence

This review follows a browser attachment from local storage through the sync client, a real local CashFlux server, and a second isolated browser profile. It also checks the Cloud setup and account-scope boundaries. The production host was queried only at its public `/v1/version` endpoint, without credentials or customer data. Its advertised API range includes this client's v1 protocol; production account data and production file transfer were not accessed.

The executable evidence is `e2e/regression/sv0_first_snapshot.spec.mjs`, `sv0_artifact_upload.spec.mjs`, `sv0_artifact_sync.spec.mjs`, `sv0_server_url.spec.mjs`, `sv0_lock_reload.spec.mjs`, and `local_artifact_migration.spec.mjs`, plus the server's blob isolation and quota tests in `internal/server/blobservice_test.go`, the blob-backed PDF snapshot test in `internal/appstate/artifact_roundtrip_test.go`, and local encrypted-store tests in `internal/artifactstore` and `internal/browserstore`. These tests use synthetic accounts and fresh local servers. Browser status text alone is never the file oracle: the upload tests inspect the server snapshot, the full roundtrip compares downloaded PNG, receipt, goal photo, and account PDF bytes with their sources, and the migration and roundtrip tests inspect raw IndexedDB records on each browser. The migration case plants both an inactive-workspace file and an unreferenced legacy file, then verifies that protected boot replaces their raw plaintext records with encrypted records.

## Current data flow

| Step | Behavior | Privacy boundary |
| --- | --- | --- |
| Local save | The app keeps the working dataset in protected browser storage. Dataset saves use a generation compare-and-swap so another tab cannot silently replace them. Large artifact bytes can live in a separate IndexedDB blob store. | New local artifact records seal bytes and MIME with the protected workspace key and bind them to the artifact ID. After protected boot, a background inventory migrates legacy plaintext records across the origin, including unreferenced files; a conditional IndexedDB write avoids replacing another tab's newer file. Any older record is also encrypted on first read before its bytes are returned. If the blob store is unavailable, bytes remain in the protected dataset. |
| First connection | Settings checks the public `/v1/version` response and establishes an account session. A first push creates an empty owned workspace row before uploading blobs. | Discovery sends no bearer token. Remote non-loopback sync requires HTTPS/WSS; loopback HTTP/WS remains available for local development. |
| File upload | `prepareBackendSyncDataset` encrypts each artifact with the App Lock passcode, uploads ciphertext under its SHA-256 hash, replaces bytes with a blob reference, then encrypts the dataset snapshot. The server links the blob to the authenticated workspace and enforces the account's storage quota. | The server receives ciphertext and `application/octet-stream`, not the filename, image MIME, or plaintext bytes for new encrypted uploads. It still sees sizes, hashes, workspace/account identifiers, and timing. |
| Blob-backed files | Before upload, the client completes the committed queue item with its matching local file bytes. It pauses sync when a required blob is missing, unreadable, or shorter than its recorded size. | A partial file cannot turn into a successful fileless snapshot. The queued metadata remains available for retry or local recovery. |
| File restore | A second device decrypts the snapshot using the same passcode, downloads each referenced blob through the authenticated workspace, checks the received ciphertext hash, decrypts it, and stores the original bytes in its encrypted local blob store before committing the lightweight dataset. | A mismatched hash or decryption error aborts the import. The browser test restored a PNG and account PDF byte-for-byte and checked the encrypted local records in both profiles. |

Image surfaces resolve their files asynchronously from the encrypted local blob store after restoration. The browser regression checks artifact thumbnails, receipt thumbnails, and a goal image against the original PNG bytes in the second profile. New receipt and goal-photo uploads also place bytes in that store before their dataset references are saved.

The server stores workspace names, device IDs, account identity, timestamps, ciphertext sizes, and blob hashes as readable metadata. Workspace names can contain sensitive words; they are **not** covered by the encrypted snapshot. Artifact encryption uses a per-install salt and a deterministic IV derived from plaintext, so an identical file uploaded twice with the same installation key produces the same ciphertext hash. That enables deduplication but reveals equality within that installation to the server. Passcode strength also matters because possession of ciphertext permits offline guessing attempts.

## Safety and recovery behavior

- Dataset and blob uploads require active encryption. The server rejects a plaintext replacement after it has seen an encrypted workspace. On migration to an encrypted snapshot, it purges plaintext snapshot history for that workspace in the same accepted transaction.
- Server workspace creation advances its version. The client now uses the returned version for the immediately following first snapshot push; a later write from another device still conflicts. A rejected local snapshot is retained as a recovery copy before the client pulls the server winner.
- After a server accepts the first snapshot, the app commits its account ownership in protected storage and lets the same app's autosave writer adopt that value. This prevents a false “another tab” read-only state without allowing another tab's owner change to pass its compare-and-swap.
- Changing the server clears the old refresh/access credentials, queue, and sync bookmarks before the new endpoint is used. The focused browser case passed after journal replay was moved off the WebCrypto callback stack: the new server had no copied account and the setup was signed out after unlock. An ordinary encrypted workspace reload also passed.
- The updated service worker bypasses account/API GET requests, caches only exact core assets and dedicated public-static paths, and removes older private cache entries when it activates. Existing worker installations retain their prior behavior until the update is accepted and activated.
- A same-browser sign-in to a different account now hides the prior account's local household screens behind an ownership gate. The protected prior copy remains available when its owner signs back in. The account-switch regression checks that the new account cannot see the prior transaction or inherit its server snapshot; using separate browser profiles remains the direct way to operate both accounts on one device.
- JSON and SQLite single-workspace backups fail when required local file bytes cannot be read. The full-install backup completes active and inactive workspace datasets with their external file bytes and aborts if any required file cannot be read. Its file reads run outside the browser click callback.

## Limits and follow-up work

1. **Legacy local attachments:** New writes are encrypted and migration waits for a committed replacement. Protected boot now scans all raw artifact keys, including orphaned records, and encrypts readable legacy entries. A record that changes during the scan is left for a later pass rather than overwritten. The scan runs in the background and logs failures; records inaccessible because App Lock is unavailable, IndexedDB is damaged, or migration fails can remain plaintext, and old browser/server backups may still contain plaintext. App Lock therefore should not yet be described as protecting *all historical* attachments. `TODOS.md` tracks the broader ENC4 work.
2. **Local blob deletion and device erasure:** Deleting an individual artifact currently removes its dataset row but not its separate local blob. Immediate deletion could break an older queued snapshot, another workspace, or undo state; a per-artifact collector still needs reachability across retained snapshots and workspaces. The earlier Settings → Data “Erase everything” action also left inactive workspaces, queued sync, files, credentials, and caches behind. The device-erasure branch now leaves the app, deletes recognized CashFlux storage across all workspace and account scopes, and verifies the inventory before acknowledging completion; it has passed disposable Chromium regressions, including two workspaces with UI-created files. This change remains undeployed, and other browser engines and the production profile have not been checked. See `docs/DEVICE_ERASURE_AUDIT.md`.
3. **Metadata confidentiality:** Encrypt or deliberately minimize workspace names and other human-entered server metadata before describing sync as fully private. The current remote-content statement is limited to dataset and new attachment *contents*.
4. **Legacy data and blob cleanup:** The client can still read legacy plaintext server blobs. A current encrypted snapshot does not prove every old blob, server backup, or operator backup has been erased. Operators must run documented retention and blob GC jobs and check their results; migration of legacy blob references needs a dedicated verification case. The undeployed blob-GC safety change prevents a failed file removal from being reported as a successful sweep and keeps concurrent uploads linked before GC can remove them. It does not discover historical orphan files left by earlier failed sweeps.
5. **Server-side backup completeness:** `/v1/account/export` returns snapshots but does not carry the blob payloads. A server export by itself is not a complete file backup. A complete encrypted server export/restore format and a restore test are needed before that endpoint is described as a file-complete recovery copy. The browser full-install backup includes inactive workspace files through local blob rehydration; `backup_multi_workspace_files.spec.mjs` verifies that files in two workspaces restore and download byte-for-byte in another browser context.
6. **Production validation:** The tests prove local protocol behavior. A credentialed production roundtrip would require a deliberately created test account and file, with explicit authorization and cleanup; no customer data should be used as a test fixture.
7. **File size and custom servers:** The PDF picker accepts up to 23 MiB so its base64 encrypted upload fits the server's default 32 MiB blob cap. A self-hosted server may configure a lower limit; a rejected upload leaves the local file and queued snapshot intact, but that file will not appear on another browser until the server limit or file size is resolved.

The implementation and tests above are the evidence for CashFlux-specific claims.
